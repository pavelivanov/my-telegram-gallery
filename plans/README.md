# Self-hosted + SaaS implementation plans

Generated by the `improve` skill on 2026-07-13 after reviewing the attached
proposal and the repository at commit `9282d53`. The working tree already had
uncommitted frontend changes (15 files, including share links, gallery caching,
and viewer work); every executor must preserve them and run the drift check in
its plan before editing.

The proposal's direction is sound: one codebase, self-host first, multi-tenancy
behind a mode, then hosted billing. The plans below keep that sequence but
correct security, storage, packaging, licensing, and Railway assumptions found
during code review.

## Executive verdict

Keep:

- one codebase with `TENANCY_MODE=single|multi` and single as default;
- one shared SaaS bot for launch, with BYO-bot deferred;
- S3 compatibility and direct transfers for hosted scale;
- self-host distribution before billing;
- Telegram Stars for in-Telegram digital subscription billing;
- suspension/reporting as launch requirements.

Change:

1. **Proxy both directions.** A GET media proxy alone does not remove bucket
   CORS because the browser still performs a presigned PUT. Proxy-mode
   self-hosting needs API upload and API delivery. Direct S3 remains available
   for SaaS.
2. **Default self-host storage to a filesystem volume.** Once upload is proxied,
   local filesystem storage is simpler than mandatory MinIO and makes the
   promised quickstart realistic. S3 remains a first-class alternative.
3. **Create upload intents.** Confirmation must accept an intent ID, not a
   client-returned key/MIME/size. The server must stat and decode the object
   before persistence and later quota accounting.
4. **Treat tenant headers/start params as selectors, not authority.** Telegram
   init data establishes user identity. Database membership authorizes admin
   access; every query carries tenant ID and database constraints prevent
   cross-tenant relationships.
5. **Use one origin for SaaS too until scale proves otherwise.** Gallery `/`,
   admin `/admin`, API `/api` removes two production CORS surfaces and three
   service deploys. A CDN/split static tier can be added later from measurements.
6. **Keep existing album links.** Use `album_<id>` for shared album deep links
   and `tenant_<slug>` for gallery-home links. There is no need to pack tenant
   and album into one fragile 64-character parameter because album IDs are
   globally unique and resolve tenant server-side.
7. **Do not accept soft quota races.** Reserve bytes before upload, verify actual
   original+variant sizes, serialize per-tenant mutations, and reconcile.
8. **Replace the license slogan with a decision.** AGPL creates a network source
   obligation but does not prohibit competing hosting. Choose AGPL + separate
   commercial licensing, a permissive license, or a counsel-drafted
   source-available license according to the actual business goal.
9. **Correct Railway economics.** Current public docs state 15% base template
   kickback and a 10% support bonus (25% total), not 50%. Treat it as a changing
   acquisition incentive, not forecast revenue.

## Direction options after launch

1. **Public web galleries**: high product leverage because the storage/media
   layer and tenant slugs will already exist, but it introduces a second auth/
   privacy model and much more abuse/search exposure. Design it separately after
   SaaS moderation is functioning.
2. **Collaborator admins**: the Membership table makes this adjacent and safer
   than adding more env IDs. Extend roles/invitations only after owner-only
   isolation tests are stable.
3. **BYO bot / white label**: potentially paid differentiation, but it requires
   encrypted-at-rest tokens, rotation, per-bot validation caching/webhooks, and
   recovery. Keep it out of the initial tenant and billing schema.
4. **Themes**: likely the cheapest paid differentiator after tenancy because the
   current frontends already centralize visual tokens; defer until plan/usage
   mechanics prove demand.

## Findings considered and rejected

- **Keep three production services for SaaS**: rejected for launch. One stateless
  app process can scale horizontally and removes CORS/build configuration. Add a
  CDN later only with measured need.
- **GET-only `MEDIA_MODE=proxy` removes storage CORS**: rejected; direct browser
  PUT still crosses origins.
- **MinIO as mandatory self-host default**: rejected after adding proxy upload.
  A filesystem volume is simpler; MinIO/S3 remains optional.
- **Trust `X-Tenant` because `start_param` established tenant**: rejected. A
  header is mutable, and start params guide navigation. Membership + scoped DB
  queries authorize mutations.
- **Store optional `Tenant.botToken` now for future BYO**: rejected. Storing a
  high-value secret without the complete encryption/rotation/webhook design
  increases risk without launch value.
- **Accept soft quota races and reconcile only at confirm**: rejected. Reserve at
  intent creation and serialize tenant accounting.
- **AGPL plus an unspecified hosted exception prevents rehosting**: rejected as
  legally/strategically imprecise. Use an approved standard or counsel-drafted
  license strategy.
- **Railway template pays 50%**: rejected; official docs currently show 15% base
  plus 10% active-support bonus.
- **Automatic public content deletion on downgrade**: rejected. Keep content
  readable and block new writes until usage fits; destructive retention needs a
  separate approved policy.

## Audit boundaries

This planning pass covered the complete small API, Prisma history/schema,
frontend API/routing/upload/share paths, package/verification setup, deployment
scripts/config, README, and the uncommitted frontend diff at a planning level.
It did **not**:

- execute a live Telegram payment, BotFather, Railway, R2, or production flow;
- inspect full Git history for credentials/ownership;
- perform a formal legal review;
- run a dependency vulnerability/license scanner;
- visually audit every existing UI state or accessibility detail;
- benchmark image processing, S3 egress, or real multi-tenant load.

Those are explicit gates in Plans 005–007 rather than assumed complete.
